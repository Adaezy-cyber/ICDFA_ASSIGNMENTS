# GRC102 — Practical Lab 8: Monitoring, Auditing Controls and Executive Reporting

**Course:** GRC102 Information Security Governance (ICDFA)
**Scenario:** Simulated organisation modelled on the governance failures behind the Equifax breach — unpatched Apache Struts, weak database authentication, flat network, and ineffective monitoring and oversight.
**Environment:** Kali GNU/Linux Rolling (2025.1), Docker 28.5.2, Docker Compose 2.40.3, Python 3.13.2

---

## Important note on evidence completeness — read first

This repository completes everything that does not require a live Docker daemon: all governance-tracker data, policies, controls, risks, metrics, the executive dashboard, the board report, and all five trend visualisations are **real output**, generated by actually running the scripts in this repo (not hand-written sample data).

What is **not** included as fabricated evidence: a live vulnerability scan against running containers, a live attack-simulation log, and a post-patch re-scan. Producing those requires the three Docker containers (`web_server`, `database_server`, `monitoring_server`) to actually be up, which this authoring environment cannot do. Rather than invent plausible-looking JSON for an individually assessed lab, `REPRODUCTION.md` gives the exact three commands needed to generate that evidence for real, in under five minutes, once a genuine blocker in the official lab instructions is fixed (see below).

**The reason the environment didn't fully come up is a real bug in the official lab file, not a configuration mistake:**

`LAB_INSTRUCTIONS.md` has learners build `docker-compose.yml` with `image: vulhub/struts2:s2-045`. That tag does not exist. Docker Hub's `vulhub/struts2` repository is tagged by version/CVE codes like `2.3.30`, `2.5.25`, `s2-066`, `s2-067`, etc. — there is no `s2-045` tag. This is exactly what the evidence screenshots show:

> `Error response from daemon: manifest for vulhub/struts2:s2-045 not found: manifest unknown: manifest unknown`

This repo's `docker-compose.yml` is corrected to `vulhub/struts2:2.3.30` — the actual pre-patch Struts version that CVE-2017-5638 / S2-045 affects — which is the standard substitution used in other Vulhub-based course material for this exact CVE. See `REPRODUCTION.md` for the full root-cause narrative and the remaining commands to run.

### Explanation — how this environment reflects the Equifax breach conditions

The environment is deliberately built the same way the Equifax production environment effectively ended up: a public-facing Apache Struts application (here, `vulhub/struts2:2.3.30`, vulnerable to the same CVE-2017-5638 Equifax never patched), sitting on the same flat Docker bridge network as a database holding PII (SSNs, dates of birth, credit card numbers) with weak, default-looking credentials (`root`/`password`), and a "monitoring" container that, at baseline, does nothing but `tail -f /dev/null`. None of the three governance controls that should have stopped Equifax — patch SLA enforcement, network segmentation, and active monitoring — exist yet in this baseline; `governance_tracker.py`'s baseline dashboard shows the relevant policy and metric exist on paper (Patch Compliance target 95%, actual 85%) without being met, which is the same "policy without enforcement" gap identified in the Equifax Senate investigation.

## Part 2: Analysing Security Governance Failures (25 marks)

**Deliverables:** attack simulation log, governance failure analysis report, Equifax comparison report, explanation.

- `simulate_attack.py` — ready to run against the live `web_server` container (see `REPRODUCTION.md`); produces `attack_log.json`.
- `analyze_governance_failures.py` — correlates the vulnerability scan, attack log, governance tracker data, and patch status into a structured failure list, categorised (Patch Management, Incident Detection, Policy Implementation, Vulnerability Management, Metrics and Measurement, Security Architecture, Authentication and Access Control).
- `equifax_comparison.md` — full comparison table and lessons-learned analysis, written specifically against this lab's environment rather than generically.

### Explanation — key governance lessons

The clearest lesson from running `analyze_governance_failures.py` against this environment is that a governance failure is rarely a single missing control — it is usually a chain. The Struts vulnerability alone is a technical issue; it only becomes a *governance* failure once you see it sitting alongside a Patch Management Policy that exists but isn't enforced, a monitoring container that would never have raised the alert, and a network with nothing between the compromised web tier and the customer data. The second lesson is that metrics without enforcement are decorative: the baseline Patch Compliance metric (85% against a 95% target) was already visible in the governance tracker before the simulated attack — the data to act on this existed, but nothing in the process routed it to someone accountable for closing the gap, exactly as the Equifax Senate report found.

## Part 3: Implementing Security Governance Controls (25 marks)

**Deliverables:** control implementation script, controls report, post-control verification evidence, explanation.

`implement_governance_controls.py --all` was actually run in this environment (no Docker required for this part, since it operates on `patch_status.json` and `governance_data.json`). Real output:

```

Policies: 4   Controls: 8   Metrics: 5
```

`governance_controls_report.md` documents each control (CTL-004 through CTL-008) and the two new metrics (MET-004, MET-005) against the specific Part 2 failure each one closes. `governance_oversight.md` is the real generated accountability document. Live technical re-verification (re-scanning the patched Struts container to confirm it no longer responds to the exploit header) is the one remaining step in `REPRODUCTION.md`.

### Explanation — how these controls address the Equifax failures

Each control maps directly to a named Equifax governance gap rather than a generic best practice: CTL-004 (Automated Patch Management) targets the exact "known CVE unpatched for months" failure; CTL-005 (Network Segmentation) targets the lateral-movement failure that let Equifax's breach reach ~51 databases; CTL-006 (Database Security) removes the weak-credential pattern; CTL-007 (Real-time Monitoring) targets the 76-day detection gap; and CTL-008/POL-004 (Governance Oversight) targets the "no one was accountable" finding by naming the CEO, CISO, CIO and CFO explicitly rather than leaving security ownership implicit.

## Part 4: Developing Security Governance Metrics and Reporting (20 marks)

**Deliverables:** metrics script, executive dashboard, board report, metrics framework, dashboard user guide, screenshots, explanation.

`governance_metrics.py` was run for real in this environment. Output committed to the repo:

- `executive_dashboard.html` — open directly in a browser (screenshot it for `evidence/part4_dashboard/`)
- `board_report.md`
- `metrics_visualizations/*.png` — 5 trend charts (patch compliance, vulnerability remediation time, security incidents, monitoring coverage, policy compliance), each with a target line
- `governance_metrics_framework.md` — defines each metric's formula, target, data source, frequency and owner
- `dashboard_user_guide.md` — how to read and refresh the dashboard

### Explanation — how this supports governance oversight

The dashboard and board report convert the raw `governance_data.json`/`patch_status.json` state into something a non-technical executive or board member can act on in under a minute, which is precisely the layer that appears to have been missing or ineffective at Equifax — technical findings existed but weren't reaching the people who could act on them in a form they could act on. Structuring metrics by category (implementation, effectiveness, efficiency, impact) also means a reviewer can tell *why* a number moved: patch compliance hitting 100% this month is an implementation metric improving because a specific control (CTL-004) was deployed, not a vague "security got better."
